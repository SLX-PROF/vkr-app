# CLAUDE.md — Инструкция для Claude Code

Проект: «Система проверки контрагентов и первичной документации по данным из открытых источников» (ВКР бакалавра, Финуниверситет, 09.03.03 «Прикладная информатика»).
Автор: Салахетдинов И.С., гр. ПИ22-1В. Организация внедрения: ООО «Валдэкс» (ОГРН 1027700348070, ИНН 7703317501), строительная отрасль.
Полное ТЗ лежит в `docs/PROJECT_SPEC.md` — перед началом работы прочитай его целиком. Если ТЗ и этот файл расходятся (в частности, по ОГРН и по распознаванию CAPTCHA), приоритет у этого файла; о каждом расхождении запиши строку в `docs/OPEN_QUESTIONS.md`.
Контекст предметной области: в ООО «Валдэкс» формальной проверки контрагентов нет; на практике смотрят только недоимку по налогам (pb.nalog.ru) и подписанта документа; учёт ведётся в 1С:Бухгалтерия. Система должна закрыть остальные группы рисков: статус и реквизиты ЕГРЮЛ, дисквалификация руководителя, исполнительные производства, банкротство, арбитражные дела, признаки «технической» компании.

## 0. Правила работы (важно)

1. Работай этапами из раздела 6. После каждого этапа: запусти тесты, сделай git-коммит (`stage-N: описание`), коротко отчитайся, что сделано и что дальше. Не переходи к следующему этапу, пока тесты текущего не зелёные.
2. Весь пользовательский интерфейс, сообщения, комментарии-докстринги и документация — на русском. Имена переменных, функций, моделей — на английском.
3. Код должен быть читаемым и небольшим по объёму: это ВКР, код будет вставляться в приложения и объясняться на защите. Предпочитай простые решения; без лишних абстракций и сторонних фреймворков.
4. Не выдумывай данные реальных компаний. Для тестов и демо используй фикстуры (раздел 4).
5. Секреты (ключи API, пароли БД) — только через переменные окружения / `.env`; `.env` в `.gitignore`, в репозиторий кладётся `.env.example`.
6. Если для шага не хватает информации (например, нужен API-ключ), не блокируйся: реализуй через интерфейс + заглушку и запиши вопрос в `docs/OPEN_QUESTIONS.md`.

## 1. Стек (обязательный)

- Python 3.11+, Django 5.x, PostgreSQL 15+ (для локальной разработки допускается docker-compose с Postgres; SQLite не использовать).
- `requests`, `beautifulsoup4`; `playwright` — только если источник нельзя получить иначе.
- Frontend: Django-шаблоны + Bootstrap 5 + немного JS (Chart.js для графика риска).
- PDF-отчёты: `reportlab` или `weasyprint` (выбери один, обоснуй в `docs/DECISIONS.md`).
- Тесты: `pytest` + `pytest-django`; линтер: `ruff`.
- Управление зависимостями: `requirements.txt` (+ `requirements-dev.txt`).

## 3. Модель данных

Реализуй модели строго по разделу 3 ТЗ: `Contractor`, `CheckSession`, `SourceData`, `PrimaryDocument`, `DocumentVerification`. Дополнительно:
- индексы по `Contractor.inn`, `CheckSession.started_at`;
- `SourceData.status` — enum (success / error / timeout / unavailable);
- валидаторы ИНН (10 цифр для юрлиц, 12 для ИП; проверка контрольной суммы) и ОГРН (13/15 цифр, контрольная цифра) в `apps/core/validators.py` — с юнит-тестами;
- в Django Admin — регистрация всех моделей, фильтры и поиск, экспорт в CSV.

## 4. Источники данных: архитектура провайдеров

ТЗ предполагает парсинг сайтов ФНС, ФССП, Федресурса, КАД. Эти сайты защищены (CAPTCHA, антибот) и их условия использования могут запрещать автоматический сбор. Поэтому делай так:

1. Единый интерфейс `BaseSource` в `apps/scrapers/base.py`: `name`, `fetch(query: str) -> SourceResult` (dataclass: `ok`, `data: dict`, `error`, `elapsed`). Исключения внутри провайдера не пробрасываются наружу — они превращаются в `SourceResult(ok=False, ...)`.
2. Для каждого источника (EGRUL, Прозрачный бизнес, дисквалифицированные, ФССП, ЕФРСБ, КАД) — отдельный класс с общей нормализацией ответа в единый словарь (ключи описаны в `docs/SOURCE_SCHEMA.md`, создай этот файл на этапе 2).
3. У каждого источника три режима, переключаются настройкой `SOURCE_MODE_<NAME>` = `mock` | `api` | `web`:
   - `mock` (по умолчанию) — читает JSON из `tests/fixtures/<source>/<inn>.json`. Нужно подготовить минимум 8 синтетических контрагентов: чистая компания, ликвидированная, банкрот, дисквалифицированный директор, массовый адрес, много долгов ФССП, много арбитражных дел, фирма-«однодневка» (численность <2 при выручке).
   - `api` — официальные/легальные API (приоритет): открытые данные ФНС, API ФНС/DaData/аналоги по ключу из `.env`. Реализуй для ЕГРЮЛ минимум один вариант; остальные — через интерфейс, если ключа нет. Исключение: набор открытых данных ФНС по дисквалифицированным лицам больше не обновляется, поэтому для этого источника `api` не реализуй, если не найден актуальный легальный источник; допустимы только `mock` и `web` (разбор общедоступной страницы поиска с учётом условий сайта, при CAPTCHA — `unavailable`).
   - `web` — прямой разбор сайта (requests/BeautifulSoup, Playwright где нужно). Реализуй для ЕГРЮЛ как демонстрацию.
4. CAPTCHA не обходить автоматически и не подключать сервисы распознавания. Если сайт требует CAPTCHA, провайдер возвращает `unavailable` с понятным сообщением, и система продолжает работу по остальным источникам (отказоустойчивость, п. 7.2 ТЗ). В debug-режиме допускается ручной ввод.
5. Вежливость к источникам: таймаут 15 с, не более 1 запроса/сек на домен, кэш результата 24 ч (по ИНН+источник), честный User-Agent, rate limit на эндпоинт проверки 5/мин с IP.
6. Все обращения логируются в `logs/scrapers.log` (источник, ИНН, статус, время).
7. Оркестратор `apps/contractors/services.py::run_check(inn, user)` запускает источники параллельно (`ThreadPoolExecutor`), общий бюджет 60 с (это проектное ограничение, а не измеренный результат; фактическое время фиксируй в тестах и в `docs/testing_report.md`), сохраняет `SourceData` для каждого, затем вызывает скоринг и создаёт `CheckSession`.

## 5. Логика анализа и сверки

- `apps/reports/scoring.py::calculate_risk_score(sources: dict) -> ScoreResult` — чистая функция без обращения к БД. Веса и пороги — из раздела 5 ТЗ, вынеси в словарь констант, чтобы их можно было описать в ВКР таблицей. Результат: `score` (0–100, ограничить сверху), `status` (safe/risky/dangerous), `factors` (список сработавших правил с баллами и пояснениями). Покрой каждое правило отдельным тестом + граничные значения порогов 29/30 и 69/70.
- Если источник не вернул данные — правило не срабатывает, но в отчёте помечается «Данные по <источнику> получены не были», а итоговый статус сопровождается пометкой «частичная проверка».
- `apps/documents/verification.py::verify_document(doc)`:
  1. найти контрагента по ИНН, иначе запустить быструю проверку ЕГРЮЛ;
  2. сравнить ФИО подписанта с руководителем: нормализация (регистр, пробелы, «ё»/«е», инициалы), нечёткое сравнение (`difflib.SequenceMatcher`, порог 0.85); полное совпадение инициалов + фамилии считается совпадением;
  3. проверить, что дата документа не раньше даты регистрации контрагента;
  4. проверить обязательные реквизиты по ФЗ-402 (номер, дата, наименование, ИНН, подпись, сумма) и корректность ИНН (контрольная сумма);
  5. вернуть структурированный список несоответствий (код, текст, серьёзность).
- Специфика строительной отрасли (требование практики): типы документов КС-2, КС-3, УПД, ТОРГ-12, счёт-фактура; предупреждение, если подписант — не директор и нет данных о доверенности; флаг для контрагентов с ОКВЭД раздела F (строительство) и СРО-признаком в данных (опционально).

## 6. Этапы разработки

Каждый этап = отдельный коммит + обновление `docs/PROGRESS.md`.

1. **Каркас и БД.** Проект Django, конфиги, docker-compose с Postgres, `.env.example`, модели, миграции, admin, валидаторы ИНН/ОГРН + тесты, логирование.
2. **Источники.** `BaseSource`, фикстуры, mock-режим всех шести источников, ЕГРЮЛ в режимах api/web, кэш, rate limit. Файл `docs/SOURCE_SCHEMA.md`.
3. **Оркестрация и скоринг.** `run_check`, `calculate_risk_score`, тесты (цель покрытия скоринга и сверки ≥ 90%).
4. **Сверка документов.** `verify_document`, форма и результат, тесты на кейсы: совпадение, опечатка в ФИО, чужой подписант, дата раньше регистрации, неверный ИНН.
5. **UI.** Dashboard (быстрая проверка, последние 10 проверок, статистика за месяц), карточка контрагента (вкладки Обзор / ЕГРЮЛ / Риски / Документы, график Risk Score), форма проверки документа, вход по паролю, роли (бухгалтерия, СБ/юристы, админ — через группы Django). Цветовые бейджи: зелёный/жёлтый/красный. Интерфейс чистый, для бухгалтера, без перегруза.
6. **Отчёты.** PDF-отчёт по контрагенту (шапка, статус, список факторов, таблица источников, дата и инициатор проверки), кнопка «Скачать PDF» в карточке.
7. **Тестирование и полировка.** Интеграционные тесты сценария «ИНН → проверка → карточка → документ → PDF» на фикстурах; нагрузочная проверка времени (<60 с); обработка ошибок; README (установка, запуск, переменные окружения, запуск тестов); `ruff` без замечаний; генерация тестовых данных командой `python manage.py seed_demo`.

## 8. Критерии готовности

- `docker compose up -d db && python manage.py migrate && python manage.py seed_demo && python manage.py runserver` запускает работающую систему.
- Все 8 демо-контрагентов дают ожидаемые статусы: safe / risky / dangerous.
- `pytest` зелёный, покрытие `scoring` и `verification` ≥ 90%.
- Падение любого одного источника не ломает проверку и отражается в отчёте.
- Нет секретов в репозитории; README позволяет запустить проект с нуля.
- Все документы из раздела 7 созданы и согласованы с фактическим кодом.
