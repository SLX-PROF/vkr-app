## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Назначение системы
Разрабатываемая информационная система (далее — ИС) предназначена для автоматизации процессов:
1.  Проверки благонадежности юридических лиц (контрагентов) перед заключением договоров.
2.  Сверки реквизитов входящей первичной учетной документации (счета, акты, накладные) с официальными данными из государственных реестров.
3.  Формирования отчетов о рисках сотрудничества с контрагентом.

### 1.2. Целевая аудитория пользователей
*   **Бухгалтерия:** Ввод данных документов, проверка соответствия подписантов.
*   **Служба безопасности / Юридический отдел:** Анализ рисков, просмотр детальных отчетов по контрагентам.
*   **Администратор:** Управление пользователями, настройка параметров проверок.

### 1.3. Технологический стек (Обязательный к применению)
*   **Язык программирования:** Python 3.11+
*   **Веб-фреймворк (Backend):** Django 5.x (ORM, Admin Panel, Authentication)
*   **База данных:** PostgreSQL 15+
*   **Библиотеки для сбора данных:**
    *   `requests` + `BeautifulSoup4` (для статических страниц)
    *   `Playwright` (только для общедоступных страниц, содержимое которых формируется скриптами и которые нельзя получить иначе)
*   **Frontend:** HTML5, CSS3, JavaScript (Bootstrap 5 для быстрого создания адаптивного интерфейса).

## 2. АРХИТЕКТУРА СИСТЕМЫ

### 2.1. Общая схема работы
Система работает по принципу «Запрос → Сбор данных → Анализ → Отчет»:
1.  Пользователь вводит ИНН/ОГРН контрагента или вводит реквизиты документа.
2.  Система обращается к модулям-провайдерам открытых источников (официальные интерфейсы и открытые данные в приоритете, разбор общедоступных страниц — при необходимости и с учётом условий использования сайтов).
3.  Полученные данные сохраняются в БД в структурированном виде.
4.  Модуль анализа сравнивает данные из документов с данными ЕГРЮЛ и рассчитывает «Индекс риска».
5.  Пользователю отображается визуальный отчет (зеленый/желтый/красный статус).

### 2.2. Структура приложения (Django Apps)
1.  **core:** Настройки проекта, общие утилиты, базовые модели.
2.  **contractors:** Логика управления карточками контрагентов, история проверок.
3.  **scrapers:** Изолированный пакет модулей для обращения к внешним API и сайтам. Каждый источник — отдельный класс.
4.  **documents:** Логика обработки первичных документов, формы ввода реквизитов, алгоритмы сверки.
5.  **reports:** Генерация PDF-отчетов и визуализация данных.

## 3. МОДЕЛЬ ДАННЫХ (БАЗА ДАННЫХ)

Поля указаны как требования к содержанию, типы данных выбираются разработчиком исходя из лучших практик Django/PostgreSQL.

### 3.1. Сущность `Contractor` (Контрагент)
*   **Уникальные идентификаторы:** ИНН (обязательно, уникально), ОГРН (опционально).
*   **Наименование:** Полное и сокращенное название.
*   **Руководитель:** ФИО директора, должность.
*   **Адрес регистрации.**
*   **Статус активности:** Действующее / Ликвидировано / В стадии банкротства.
*   **Дата последнего обновления данных из ЕГРЮЛ.**

### 3.2. Сущность `CheckSession` (Сеанс проверки)
*   **Связь:** ForeignKey на `Contractor`.
*   **Дата и время начала проверки.**
*   **Инициатор:** ForeignKey на User (кто запустил проверку).
*   **Итоговый статус:** Безопасен / Рискованный / Опасный.
*   **Итоговый балл риска:** Integer (0-100).

### 3.3. Сущность `SourceData` (Сырые данные из источника)
*   **Связь:** ForeignKey на `CheckSession`.
*   **Название источника:** Строка (например, "ЕГРЮЛ", "ФССП").
*   **JSON-ответ:** JSONField (весь распарсенный объект от источника для анализа и аудита).
*   **Статус запроса:** Успех / Ошибка / Таймаут / Недоступен.
*   **Время выполнения запроса.**

### 3.4. Сущность `PrimaryDocument` (Первичный документ)
*   **Тип документа:** Выбор из списка (Счет, Акт КС-2, Справка КС-3, Накладная ТОРГ-12, УПД, Счет-фактура).
*   **Номер и дата документа.**
*   **ИНН контрагента в документе.**
*   **ФИО подписанта в документе.**
*   **Должность подписанта в документе.**
*   **Сумма документа.**
*   **Файл (опционально):** Ссылка на загруженный PDF/скан.

### 3.5. Сущность `DocumentVerification` (Результат сверки документа)
*   **Связь:** OneToOne с `PrimaryDocument`.
*   **Связь:** ForeignKey на найденного `Contractor` (если ИНН совпал).
*   **Результат сверки ФИО:** Совпадает / Не совпадает / Нет данных.
*   **Результат сверки полномочий:** Подписант является директором / нет.
*   **Список выявленных несоответствий:** JSONField (детальное описание ошибок).

## 4. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ К МОДУЛЯМ СБОРА ДАННЫХ (SCRAPERS)

Каждый модуль реализует единый интерфейс (метод `fetch(query)`), возвращающий структуру с полями «успех», «данные», «ошибка», «время». Обработка ошибок (таймауты, блокировки IP, требование CAPTCHA) обязательна внутри каждого модуля: ошибка источника не должна прерывать проверку. Каждый источник поддерживает режимы `mock`, `api`, `web`.

### 4.1. Модуль `EGRUL_Scraper` (ЕГРЮЛ)
*   **Источник:** Сервис ФНС России (`egrul.nalog.ru`).
*   **Входные данные:** ИНН или ОГРН.
*   **Цель сбора:** Сведения ЕГРЮЛ в машиночитаемом виде (официальный интерфейс или открытые данные) либо разбор общедоступной страницы результатов поиска.
*   **Критически важные поля:** Статус ликвидации, ФИО руководителя, адрес, ОКВЭД, сведения о массовости адреса/руководителя.
*   **Техническое требование:** CAPTCHA автоматически не обходится и сервисы распознавания не используются. Если источник требует CAPTCHA, модуль возвращает статус «недоступен», проверка продолжается по остальным источникам. Кэширование результата на 24 часа.

### 4.2. Модуль `TransparentBusiness_Scraper` (Прозрачный бизнес)
*   **Источник:** Сервис ФНС (`pb.nalog.ru`) и открытые данные ФНС.
*   **Цель сбора:** Среднесписочная численность сотрудников, сумма налогов, режим налогообложения, наличие недоимки.
*   **Логика анализа:** Если численность < 5 человек при обороте > 10 млн руб. — флаг «Высокий риск фиктивности».

### 4.3. Модуль `Disqualified_Scraper` (Реестр дисквалифицированных лиц)
*   **Источник:** Сервис ФНС (реестр ведёт ФНС России).
*   **Цель сбора:** Проверка, находится ли ФИО руководителя контрагента в реестре дисквалифицированных лиц.
*   **Логика:** Точное совпадение ФИО. При наличии записи — критическая ошибка.
*   **Примечание:** набор открытых данных ФНС по дисквалифицированным лицам больше не обновляется, режим `api` не реализуется без найденного актуального источника.

### 4.4. Модуль `FSSP_Scraper` (ФССП - Долги)
*   **Источник:** Банк данных исполнительных производств (`fssp.gov.ru`).
*   **Цель сбора:** Наличие активных исполнительных производств, общая сумма задолженности.
*   **Техническое требование:** Сайт защищён от автоматических запросов. Допускается официальный интерфейс (если доступен) или разбор общедоступной страницы с соблюдением условий использования и ограничения частоты запросов. Если доступ закрыт защитой (CAPTCHA), возвращается статус «недоступен»; эмуляция действий человека и обход защиты не применяются.

### 4.5. Модуль `EFRSB_Scraper` (Банкротство)
*   **Источник:** Федресурс (`fedresurs.ru`, раздел ЕФРСБ `bankrot.fedresurs.ru`).
*   **Цель сбора:** Сообщения о введении процедур наблюдения, конкурсного производства, финансового оздоровления.
*   **Логика:** Поиск по ИНН должника.

### 4.6. Модуль `KadArbitr_Scraper` (Арбитражные дела)
*   **Источник:** Картотека арбитражных дел (`kad.arbitr.ru`).
*   **Цель сбора:** Количество исков, выступление ответчиком/истцом, наличие непогашенных судебных актов.
*   **Техническое требование:** Содержимое формируется скриптами; допускается Playwright для общедоступных страниц с ожиданием загрузки элементов. Парсинг только сводной статистики (количество дел). При защите от автоматических запросов — статус «недоступен».

## 5. ЛОГИКА АНАЛИЗА И ОЦЕНКИ РИСКОВ

Система рассчитывает **Risk Score** (0–100 баллов). Чем выше балл, тем опаснее контрагент.

### 5.1. Алгоритм начисления баллов (Весовые коэффициенты)
Функция `calculate_risk_score(data_sources_dict)` суммирует штрафы (итог ограничивается 100):

1.  **Статус ЕГРЮЛ:**
    *   Ликвидировано / Исключено из реестра: **+100 баллов** (Критический стоп-фактор).
    *   В стадии банкротства (по ЕФРСБ): **+80 баллов**.
2.  **Дисквалификация руководителя:**
    *   Найден в реестре: **+50 баллов**.
3.  **Массовость (по данным Прозрачного бизнеса/ЕГРЮЛ):**
    *   Массовый руководитель (>5 фирм): **+20 баллов**.
    *   Массовый адрес (>10 фирм): **+10 баллов**.
4.  **Долги (ФССП):**
    *   Задолженность до 100 тыс. руб.: **+10 баллов**.
    *   Задолженность свыше 100 тыс. руб.: **+30 баллов**.
    *   Более 5 активных производств: **+20 баллов**.
5.  **Судебные споры (Картотека):**
    *   Более 10 исков за последний год: **+15 баллов**.
    *   Наличие проигранных дел с крупными суммами: **+25 баллов**.
6.  **Численность персонала:**
    *   Менее 2 сотрудников при наличии выручки: **+15 баллов** (признак технической компании).

### 5.2. Интерпретация результата
*   **0–29 баллов:** Статус «Безопасен» (Зеленый). Рекомендовано к сотрудничеству.
*   **30–69 баллов:** Статус «Рискованный» (Желтый). Требуется дополнительная проверка службой безопасности.
*   **70–100 баллов:** Статус «Опасный» (Красный). Сотрудничество не рекомендовано.

### 5.3. Логика сверки первичных документов
1.  Поиск контрагента в локальной БД по ИНН из документа.
2.  Если не найден — запуск быстрой проверки по ЕГРЮЛ.
3.  Сравнение строки `signer_name` из документа с полем `director_name` из последней успешной проверки ЕГРЮЛ.
4.  Если ФИО различаются (нечеткое сравнение, игнор регистр и пробелы) — предупреждение: *"Подписант не является действующим руководителем согласно данным ЕГРЮЛ"*. Если подписант не директор, выводится напоминание проверить доверенность или приказ.
5.  Проверка даты документа: если дата раньше даты регистрации контрагента в ЕГРЮЛ — ошибка.

## 6. ТРЕБОВАНИЯ К ПОЛЬЗОВАТЕЛЬСКОМУ ИНТЕРФЕЙСУ (UI)

Интерфейс минималистичный, понятный бухгалтеру. Bootstrap 5.

### 6.1. Главная страница (Dashboard)
*   Виджет «Быстрая проверка»: одно поле ввода (ИНН/ОГРН) и кнопка «Проверить».
*   Таблица последних 10 проверок: [Контрагент, Дата, Статус (цветовой индикатор), Балл].
*   Статистика: количество безопасных/рисковых контрагентов за месяц.

### 6.2. Карточка контрагента
*   Шапка: Название, ИНН, ОГРН, Текущий статус (цветной бейдж).
*   Вкладки: **Обзор** (график Risk Score во времени, краткие выводы); **ЕГРЮЛ** (руководитель, учредители, виды деятельности); **Риски** (список выявленных нарушений со ссылками на первоисточники); **Документы** (история проверок документов).

### 6.3. Форма проверки документа
*   Поля: Тип документа, Номер, Дата, ИНН, Сумма, ФИО подписанта, Должность.
*   Кнопка «Сверить».
*   Результат: зелёная галочка «Соответствует» или красный список расхождений с пояснениями.

### 6.4. Административная панель (Django Admin)
*   Просмотр всех записей `SourceData` для отладки модулей.
*   Управление пользователями и правами доступа.
*   Экспорт данных в CSV/Excel.

## 7. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

1.  **Производительность:** Полная проверка одного контрагента (все 6 источников) проектируется с бюджетом не более 60 секунд (фактическое время фиксируется при тестировании).
2.  **Отказоустойчивость:** Если один из источников недоступен (например, ФССП), система продолжает работу остальных модулей и выводит частичный отчет с пометкой «Данные по ФССП получены не были».
3.  **Безопасность:**
    *   Парольная защита входа.
    *   Хранение паролей в хэшированном виде (bcrypt/pbkdf2).
    *   Защита от SQL-инъекций (ORM Django).
    *   Rate limiting на endpoint проверки (не более 5 запросов в минуту с одного IP) и ограничение частоты запросов к внешним источникам.
4.  **Логируемость:** Все действия модулей (успешные запросы, ошибки, таймауты) записываются в `logs/scrapers.log`.
5.  **Персональные данные:** ФИО руководителей и участников обрабатываются в соответствии с 152-ФЗ; хранятся только сведения, необходимые для проверки; демонстрация выполняется на синтетических данных.
